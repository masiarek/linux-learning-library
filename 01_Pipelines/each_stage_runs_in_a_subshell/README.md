# Each stage runs in a subshell

**Level:** 101 · you have counted lines inside `… | while read line` and found the count back at 0 after `done`

**One line:** In bash every stage of a pipeline runs in a child process, the last one too, so `echo alma | read v` sets `v` in a process that exits at once, and the shell's own `v` never changes. zsh runs the last stage in the shell itself, and fish runs its own builtins and blocks in the shell at any stage, so the same line works in both. bash 4.2's `shopt -s lastpipe` does what zsh does, but only while job control is off, and the Mac's bash 3.2 does not have it.

## Measured

A pipe joins two running processes, so the shell starts a process for each stage. bash does that even when the stage is shell code of its own, such as `read` or a `while` loop: it runs the stage in a copy of itself. The copy starts with the shell's variables, and whatever it changes is lost when it exits:

<!-- output:subshell_stage_sh -->
*Verified output of [`subshell_stage_sh.sh`](examples/subshell_stage_sh.sh), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ v=before; echo alma | read v; echo "v is $v"
v is before

$ n=0; printf "alma\ndarkfi\nfedora\n" | while read -r line; do n=$((n + 1)); done; echo "counted $n"
counted 0

$ printf "alma\ndarkfi\nfedora\n" | { n=0; while read -r line; do n=$((n + 1)); done; echo "counted $n, inside the stage"; }
counted 3, inside the stage

$ n=0; while read -r line; do n=$((n + 1)); done < <(printf "alma\ndarkfi\nfedora\n"); echo "counted $n"
counted 3

$ v=before; { v=alma; } | cat; echo "v is $v"
v is before

$ echo alma | exit 3; echo "still running, status $?"
still running, status 3
```
<!-- /output -->

- **`v is before`.** `read` did read `alma`, into the `v` of a child bash that then exited. The parent's `v` was not touched. It was not emptied either: it kept its old value, so a script that set `v` earlier carries on with a stale value and no error.
- **`counted 0`** is the same thing, one loop long. The whole `while` loop was the child. It counted to 3, and the count went when the child did.
- **Keep the reading and the using in one stage.** The braces make the loop and its `echo` a single stage, run by a single child, so the child prints its own count before it exits: `counted 3, inside the stage`. The value still never reaches the shell.
- **Or do not pipe into the loop.** `done < <(printf …)` feeds the loop from a process substitution: the loop runs in the shell and the command producing the lines runs beside it. `done < file` does the same for a file. bash 3.2 has process substitution, so this fix works on a Mac too.
- **The first stage is a child as well.** `{ v=alma; } | cat` set `v` in a child, and the shell's `v` is still `before`.
- **`exit` in a stage ends that stage.** `echo alma | exit 3` ended the child that ran `exit`. The script carried on, and `$?`, the pipeline's status, is the child's 3.

## On a Mac

The key above is shared: `/bin/bash` 3.2 runs every stage in a child exactly as bash 5.2 does. What 3.2 lacks is the option that changes it. bash 4.2 added `shopt -s lastpipe`, which runs the last stage in the shell itself. Each line below runs in a child bash, so an option set on one line cannot reach the next:

<!-- output:subshell_stage_lastpipe_sh -->
*Verified output of [`subshell_stage_lastpipe_sh.sh`](examples/subshell_stage_lastpipe_sh.sh) on **Linux** — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ bash -c 'v=before; echo alma | read v; echo "v is $v"'
v is before

$ bash -c 'shopt -s lastpipe; v=before; echo alma | read v; echo "v is $v"'
v is alma

$ bash -c 'set -m; shopt -s lastpipe; v=before; echo alma | read v; echo "v is $v"'
v is before
```

*Verified output of [`subshell_stage_lastpipe_sh.sh`](examples/subshell_stage_lastpipe_sh.sh) on **macOS** — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ bash -c 'v=before; echo alma | read v; echo "v is $v"'
v is before

$ bash -c 'shopt -s lastpipe; v=before; echo alma | read v; echo "v is $v"'
bash: line 0: shopt: lastpipe: invalid shell option name
v is before

$ bash -c 'set -m; shopt -s lastpipe; v=before; echo alma | read v; echo "v is $v"'
bash: line 0: shopt: lastpipe: invalid shell option name
v is before
```
<!-- /output -->

- **On Linux, `lastpipe` works:** `echo alma | read v` set `v`.
- **Unless job control is on.** The third line adds `set -m`, which turns job control on, and `v` is `before` again. The bash manual gives the condition: the last stage runs in the shell only while job control is not active. It is off in a script and on in an interactive shell, so `shopt -s lastpipe` typed at a prompt does not change what the prompt does.
- **On the Mac, bash 3.2 rejects the option name**, prints an error, and carries on with the old behaviour. A script that relies on `lastpipe` does not stop there. It runs to the end with `v is before`.

`< <(…)` from the list above is the spelling that behaves the same on both machines.

## In zsh and fish

**zsh** runs the last stage of a pipeline in the shell itself when that stage is a builtin or other shell code, so the line bash gets wrong works. The stages before it are still child processes:

<!-- output:subshell_stage_zsh -->
*Verified output of [`subshell_stage_zsh.zsh`](examples/subshell_stage_zsh.zsh), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ v=before; echo alma | read v; echo "v is $v"
v is alma

$ n=0; printf "alma\ndarkfi\nfedora\n" | while read -r line; do n=$((n + 1)); done; echo "counted $n"
counted 3

$ v=before; { v=alma; } | cat; echo "v is $v"
v is before

$ zsh -fc 'echo alma | exit 3; echo "still running"'
(exit status 3)
```
<!-- /output -->

`read` and the `while` loop ran in zsh itself. `{ v=alma; } | cat` is the other half of the rule: the braces are the first stage, so they ran in a child, and `v` stayed `before`. And `exit` in the last stage is the shell's own `exit`. The child zsh ended with status 3 and never printed `still running`. So `… | exit` in a bash script ends only a subshell, and the same line in a zsh script ends the script.

**fish** ran every one of these inside its own process, in the first stage as well as the last. Only external commands got processes of their own:

<!-- output:subshell_stage_fish -->
*Verified output of [`subshell_stage_fish.fish`](examples/subshell_stage_fish.fish), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ set v before; echo alma | read v; echo "v is $v"
v is alma

$ set n 0; printf "alma\ndarkfi\nfedora\n" | while read -l line; set n (math $n + 1); end; echo "counted $n"
counted 3

$ set v before; begin; set v alma; end | cat; echo "v is $v"
v is alma

$ fish --no-config -c 'echo alma | exit 3; echo "still running"'
(exit status 3)
```
<!-- /output -->

All three set the variable, including `begin; set v alma; end | cat`, where the block is the first stage, the case zsh still runs in a child. `exit` in a stage ended fish itself. The same property is why a fish loop that feeds `head` keeps running after `head` has gone, in [head closes the pipe early](../head_closes_the_pipe_early/README.md).

| | bash | zsh | fish |
|---|---|---|---|
| `echo alma \| read v` sets `v` | no | yes | yes |
| a count kept inside `… \| while read` survives `done` | no | yes | yes |
| a variable set in the first stage survives | no | no | yes |
| `exit` in the last stage ends | that stage | the shell | the shell |

A habit from zsh or fish (`… | read v`) fails silently in bash: no error, just the old value. In bash, take the pipe out with `< <(…)`, which behaved the same in 3.2 and 5.2.
