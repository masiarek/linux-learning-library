# `sed` writes to stdout, not to the file

**Level:** 101 · for anyone who has run a `sed` line, seen the right answer scroll past, and then found the file unchanged

**One line:** `sed 's/a/b/' file` prints a *changed copy* and leaves `file` exactly as it was — and the flag that does change the file, `-i`, is the one thing in this chapter each machine spells differently: `sed -i` on Linux, `sed -i ''` on a Mac, and `sed -i.bak` on both.

`sed` is a filter. It reads lines, applies an edit to each, writes the result onward, and never touches the file it read from unless you go out of your way to ask. That is why it composes: `sed` in the middle of a pipeline is the whole point of it, and a program that rewrote its input would be useless there.

## Measured

A small log, and the four things people use `sed` for: substitute, substitute everywhere, pull fields out with a group, and throw lines away.

Four things to read off it:

- **`s/REGEX/REPLACEMENT/` changes the first match on each line**, not every match. `/g` changes all of them, and a number changes the *n*th one: `s/a/X/2` leaves the first `a` alone.
- **A line that does not match is passed through untouched.** The `Accepted publickey` line comes out of every command above the way it went in. `sed` prints every line unless you tell it not to.
- **`-E` turns on extended expressions**, where `(…)` groups, `+` repeats and `|` alternates without backslashes, and `\1`, `\2`, `\3` in the replacement are the groups. `-E` is the spelling both machines take; GNU's own is `-r`, and writing `-E` costs nothing.
- **`-n` plus `p` prints only what matched**, which is the difference between a report and a log with some lines rewritten. With `-n`, `sed` prints nothing on its own, and `s/…/…/p` prints just the lines the substitution changed. `/pattern/!d` — delete every line that does *not* match — is the other way to say it, and is what the [Missing Semester ↗](https://missing.csail.mit.edu/2019/data-wrangling/) lecture reaches for.

And the last command is the point of the page: `cat log.txt` after all of that, unchanged.

## On a Mac

Everything above is a shared key — the two `sed`s agree on all of it. Changing the file is where they part, and they part in both directions:

GNU `sed` takes an *optional* suffix, so `-i` on its own is in-place with no backup, and `-i.bak` keeps one. BSD `sed` takes a *required* argument, which may be the empty string, so in-place with no backup is `-i ''`. Each machine's habit is an error on the other, and the errors are unhelpful in the way only a misparsed command line can be: the Mac reads `one.txt` as the editing script and reports `invalid command code o`, while Linux reads `s/alpha/ALPHA/` as a file name and cannot open it. Neither one edits anything.

**`sed -i.bak` is the line to write.** A suffix, attached to the flag, is in-place editing on both machines, and it leaves the original next to the new file. The other portable answer is the one that existed before `-i` did: write to a new file and `mv` it over the old one, which is what `-i` does internally anyway.

What you must not write is the shortcut in the last two commands. Redirecting into the file you are reading truncates it *before* `sed` starts, so the command reads an empty file and writes an empty file, with status 0 and not a word of complaint. That is [Redirection truncates first](../../02_Redirection/redirection_truncates_first/README.md), measured, and it is exercise 3 of the lecture this chapter follows.

## In zsh and fish

Nothing changes. `sed` is an external program, and every `sed` program here is in single quotes, which mean the same thing in bash, zsh and fish: hand the bytes over untouched. The page that measures that in all three shells is [the `awk` program goes in single quotes](../the_program_goes_in_single_quotes/README.md) — its trap is `sed`'s trap too, because `sed 's/x/\1/'` in double quotes is a shell substitution waiting to happen.

The one fish-shaped difference is how you check the result: `echo $status`, never `echo $?`, which fish rejects with a message naming the right variable.

## If you are coming from another library

- **Perl.** `perl -pe 's/…/…/'` is `sed` with a real language behind the slashes, and `perl -i -pe` is in-place editing that is spelled the same on every machine. The [Perl library ↗](https://masiarek.github.io/perl-learning-library/) covers the one-liner switches.
- **Encodings.** [The tools chapter ↗](https://masiarek.github.io/encodings-learning-library/11_Tools/index.html) runs `sed`, `awk`, `cut` and `sort` over text that is not ASCII, where a range like `[a-z]` stops meaning what it looks like.
- **Python.** A rewrite-this-file script in Python has the same hazard with a different name: open for reading and writing at once, and you have truncated it.
