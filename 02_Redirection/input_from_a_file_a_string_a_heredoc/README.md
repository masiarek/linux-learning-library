# Input from a file, a string, a here-document

**Level:** 101 · you have written `done < file` at the end of a loop and wondered what `<<<` is

**One line:** `<` points descriptor 0 at a file the *shell* opens, so the command never learns the file's name, and a missing file is the shell's error. `<<<` feeds a string plus a newline, and `<<EOF` feeds the lines up to `EOF`, expanding `$name` unless the delimiter is quoted. bash and zsh share all three. fish has only `<`: the other two are parse errors there, and a pipe from `echo` or `printf` takes their place.

## Measured

*Verified output of [`redir_stdin_sh.sh`](examples/redir_stdin_sh.sh), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ printf "alma\ndarkfi\n" > names.txt

$ grep -H alma names.txt
names.txt:alma

$ grep -H alma < names.txt
(standard input):alma

$ cat nosuch
cat: nosuch: No such file or directory

$ cat < nosuch
redir_stdin_sh.sh: line 6: nosuch: No such file or directory

$ tr a-z A-Z < names.txt
ALMA
DARKFI

$ while read -r name; do echo "name: $name"; done < names.txt
name: alma
name: darkfi

$ echo aaa > a.txt; echo bbb > b.txt; cat < a.txt < b.txt
bbb

$ tr a-z A-Z <<< "one line"
ONE LINE

$ cat <<< hi | wc -c | tr -d " "
3

$ name=world
cat <<EOF
hello $name
EOF
hello world

$ cat <<"EOF"
hello $name
EOF
hello $name
```
<!-- /output -->

- **The command does not see the file name.** `grep -H` prints the name of the file each match came from. Given `names.txt` as an argument, it said `names.txt`. Given `< names.txt`, `grep` was handed only descriptor 0, and it said `(standard input)`.
- **Who complains.** `cat nosuch` is `cat` failing to open a file, under its own name. `cat < nosuch` never started `cat`: the shell failed to open the file and reported it under the script's name.
- **`tr` reads only stdin**, so `<` is how you give it a file.
- **`while read … done < names.txt`** points descriptor 0 at the file for the whole loop, and each `read` takes the next line.
- **Two `<` on one command:** the last one won, and `cat` saw only `b.txt`.
- **`<<<` adds a newline.** `hi` is two bytes, and `cat <<< hi` passed on three.
- **`<<EOF` expanded `$name`; `<<"EOF"` did not.** With the delimiter quoted, the body is literal text.

## On a Mac

Nothing changes. The key is shared: bash 3.2 already has `<<<`, and BSD `grep -H` names standard input exactly as GNU `grep` does.

## In zsh and fish

**zsh** is the same, except in one place:

<!-- output:redir_stdin_zsh -->
*Verified output of [`redir_stdin_zsh.zsh`](examples/redir_stdin_zsh.zsh), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ printf "alma\ndarkfi\n" > names.txt

$ cat < nosuch
(eval):1: no such file or directory: nosuch

$ while read -r name; do echo "name: $name"; done < names.txt
name: alma
name: darkfi

$ echo aaa > a.txt; echo bbb > b.txt; cat < a.txt < b.txt
aaa
bbb

$ tr a-z A-Z <<< "one line"
ONE LINE

$ name=world
cat <<EOF
hello $name
EOF
hello world
```
<!-- /output -->

`cat < a.txt < b.txt` printed both files. With two input redirections on one command, zsh opens both and feeds them in order, like `cat a.txt b.txt |`. This is its `MULTIOS` option, on by default. bash gave `cat` only the last file. The missing-file error is zsh's own wording, `no such file or directory: nosuch`.

**fish** has `<` and nothing else from this page:

<!-- output:redir_stdin_fish -->
*Verified output of [`redir_stdin_fish.fish`](examples/redir_stdin_fish.fish), identical on Linux and macOS — regenerated by `tools/run_examples.py`, never hand-typed.*

```text
$ printf "alma\ndarkfi\n" > names.txt

$ grep -H alma < names.txt
(standard input):alma

$ while read -l name; echo "name: $name"; end < names.txt
name: alma
name: darkfi

$ echo aaa > a.txt; echo bbb > b.txt; cat < a.txt < b.txt
bbb

$ cat < nosuch; echo "status $status"
warning: An error occurred while redirecting file 'nosuch'
warning: Path 'nosuch' does not exist
status 1

$ tr a-z A-Z <<< "one line"
fish: Expected a string, but found a redirection
tr a-z A-Z <<< "one line"
            ^
(exit status 127)

$ cat <<EOF
hello
EOF
fish: Expected a string, but found a redirection
cat <<EOF
     ^
(exit status 127)

$ echo "one line" | tr a-z A-Z
ONE LINE

$ echo hi | wc -c | tr -d " "
3

$ set name world; printf "%s\n" "hello $name" "second line" | cat
hello world
second line

$ set name world; echo "hello $name
second line" | cat
hello world
second line

$ set name world; echo 'hello $name' | cat
hello $name
```
<!-- /output -->

- `<` and `while read -l … end < file` work as in bash, and two `<` keep only the last.
- A missing file gets two warnings from fish itself, and status 1.
- `<<<` and `<<EOF` are rejected before the line runs, with status 127. The caret sits under the second `<`: fish took the first `<` as a redirection, then found another redirection where it wanted a file name.
- **The fish way is a pipe.** `echo "one line" |` gives the same three bytes for `hi` as `<<<` did, newline included. For several lines, use `printf "%s\n"` with one argument per line, or a double-quoted string that runs over several lines. Both expand `$name`. Single quotes do not, which makes them fish's counterpart of `<<"EOF"`.

| | bash | zsh | fish |
|---|---|---|---|
| from a file | `< f` | `< f`; `< a < b` reads both | `< f` |
| a string, plus a newline | `<<< "text"` | `<<< "text"` | `echo "text" \|` |
| lines, with `$name` expanded | `<<EOF` | `<<EOF` | `printf "%s\n" … \|`, or a multi-line `"…"` |
| lines, literally | `<<"EOF"` | `<<"EOF"` | `'…' \|` |
