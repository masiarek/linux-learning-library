# sudo tee writes where redirection cannot

**Level:** 201 · you have typed `sudo echo … > /etc/…` and got "Permission denied"

**One line:** In `cmd > file` your shell opens the file before `cmd` starts, so a failed open means `cmd` never runs and the error is the shell's. In `cmd | tee file`, `tee` opens the file, with `tee`'s permissions. That is the whole reason `echo x | sudo tee /etc/f` works where `sudo echo x > /etc/f` does not.

## Measured

No `sudo` runs here: CI has no password to give it, and neither has the Mac these pages were recorded on. A directory with its write permission removed (`chmod 555`) plays the part of `/etc`:

```text

$ echo "new line" > locked/notes.txt; echo "status $?"

status 1

$ echo "new line" | tee locked/notes.txt; echo "PIPESTATUS ${PIPESTATUS[*]}"
tee: locked/notes.txt: Permission denied
new line
PIPESTATUS 0 1

$ rm -f ran; sh -c "touch ran; echo new line" > locked/notes.txt; if [ -e ran ]; then echo "the command ran"; else echo "the command never ran"; fi
tee_sudo_sh.sh: line 6: locked/notes.txt: Permission denied
the command never ran

$ rm -f ran; sh -c "touch ran; echo new line" | tee locked/notes.txt > /dev/null; if [ -e ran ]; then echo "the command ran"; else echo "the command never ran"; fi
tee: locked/notes.txt: Permission denied
the command ran

$ chmod 755 locked

$ echo "new line" | tee locked/notes.txt > /dev/null; echo "another line" | tee -a locked/notes.txt > /dev/null; cat locked/notes.txt
new line
another line
```
<!-- /output -->

- **`>` fails in the shell.** The message carries the script's name and line number, not `echo`'s, and the status is 1.
- **`| tee` fails in `tee`.** `tee: locked/notes.txt: Permission denied` is `tee`'s own message. `tee` still passed `new line` on to its stdout, and `PIPESTATUS` shows `echo` succeeded and `tee` failed.
- **Did the command run?** `sh -c "touch ran; …"` leaves a file named `ran` if it runs. With `>` there was no `ran`, so the command was never started: the redirection failed first. With `| tee` it ran, and only the copy into the file failed.
- **Once the directory is writable, both halves work:** `tee` writes the file and `tee -a` appends to it, while `> /dev/null` keeps the copy off the screen.

## Where sudo comes in (not run here)

With `sudo` in front, the same rule decides. These three lines are explanation, not a verified example:

```bash
sudo echo "127.0.0.1 test" > /etc/hosts                     # fails: your shell opens /etc/hosts, as you
echo "127.0.0.1 test" | sudo tee -a /etc/hosts > /dev/null  # works: tee opens it, as root
sudo sh -c 'echo "127.0.0.1 test" >> /etc/hosts'            # works: the >> belongs to a shell running as root
```

In the first line, `sudo` gives root to `echo`, which never needed it. The `>` belongs to the shell you typed into, and that shell opens `/etc/hosts` with your permissions before it starts `sudo` at all. That is the "never ran" case above. In the second, the file is an *argument*, so the program that opens it is the one running as root. `-a` matters: without it, `tee` empties `/etc/hosts` first, as the previous lesson measured. The third moves the whole redirection into a shell that already has root, which works but means quoting a command inside a string.

## On a Mac

Nothing changes. The key is shared: BSD `tee` and GNU `tee` word the refusal identically, and bash 3.2 reports the failed redirection in the same words as bash 5.2.

fish reports a failed redirection on its own stderr, which the script's `eval … 2>&1` cannot catch, so those two lines run in a child fish, where a reader's terminal would show them. The answer is the same: with `>`, `sh` never ran.
