# The signals you cannot catch

**Level:** 201 · for anyone who has pressed Ctrl-C twice and waited

**One line:** `trap` catches SIGINT and SIGQUIT in every shell here, all three shells accept `trap … KILL` without a word of complaint, none of them can honour it — and there is a *third* way a handler silently never runs that has nothing to do with the kernel, where bash and zsh disagree.

Press Ctrl-C at a program that has taken SIGINT over and the counter keeps counting. Press it again and it counts faster. The question this page answers is what does work, and the answer is in three parts: what a shell can trap, what the kernel will not let it trap, and what a shell *says* it has trapped while quietly doing nothing.

A shell script's handler is a `trap`:

```bash
trap 'echo "caught SIGINT -- not stopping"' INT
```

That one line is the whole mechanism, and it takes a signal *name*. The number behind the name is where the portability goes — SIGKILL is 9 everywhere worth caring about, and SIGSTOP is 17 on macOS and 19 on Linux.

## Measured

Nothing below sleeps a guessed amount: each step waits for a file the previous one wrote, and the signals are sent with `kill` rather than typed.

--------------------------------------------------------------

--------------------------------------------------------------
$ kill -l KILL

Linux says 19, which is the whole difference between the two columns on
this page. Name signals in a script; never number them.

5. The other one nothing can catch
--------------------------------------------------------------
SIGSTOP suspends a process and is equally uncatchable. The difference is
that it is reversible:

$ ps -o state= -p "$victim" | tr -d " " | cut -c1
T

$ ps -o state= -p "$victim" | tr -d " " | cut -c1
S

T is stopped, and the process still exists -- still holding its memory,
its open files and its place in the process table. Only SIGCONT starts
it again. That pair is what Ctrl-Z and fg are made of, which is why they
are not in a trap table.

The same trap worked in section 1, where this script was in front. And

child written in zsh or fish catches the signal, because neither honours
that rule. So a wrapper script can work when you test it by hand, work
under zsh, and go quiet the day it is backgrounded under bash.

## What the run shows

**Sections 1 and 2 are the pair worth keeping.** bash accepted four `trap` lines and honoured three. SIGKILL is never delivered to the process at all — the kernel acts on it — so there is no moment at which a handler could run and no last words to write. A shell that accepts the trap is doing exactly what POSIX permits, because trapping SIGKILL is *undefined* rather than an error, so nothing tells you. SIGSTOP is the other one, and section 5 shows the difference: uncatchable too, but reversible, and the process sits in state `T` still holding its memory and its open files until SIGCONT arrives. That pair is what Ctrl-Z and `fg` are made of.

**128 + N is the arithmetic to memorise.** Section 3 measures it rather than asserting it. A `137` in a CI log is very rarely a mystery: 137 − 128 = 9, and something sent SIGKILL — usually the out-of-memory killer. `143` is 15, SIGTERM, a shutdown that asked politely first. `130` is 2, somebody's Ctrl-C.

**Section 6 is the one that looks like your bug.** The same script that caught SIGINT perfectly in section 1 catches nothing when it is started in the background. No kernel rule is involved. A shell starting a background job sets that child's SIGINT and SIGQUIT to **ignored** before it execs, and POSIX says a signal that was already ignored when a shell started can never be trapped, reset or caught afterwards. `trap` returns success and does nothing.

That last one is where the shells stop agreeing, so it is worth stating as a table. The **child's** shell decides; the parent's makes no difference, measured every way round:

| The backgrounded script is | Its SIGINT handler |
|---|---|
| `#!/usr/bin/env bash` | never runs — bash honours the POSIX rule |
| `#!/usr/bin/env zsh` | runs — zsh installs the trap anyway |
| `#!/usr/bin/env fish` | runs — fish does the same |

So a wrapper script whose Ctrl-C handling works under zsh can go silent the day somebody changes its first line to bash, with nothing printed about it anywhere.

## On a Mac

Two differences, and one of them is the reason the block above has two columns.

`kill -l STOP` answers **17** on macOS and **19** on Linux. SIGSTOP is one of the signals POSIX numbers differently between systems, which is the concrete reason to write `kill -STOP` and `trap … STOP` and never `kill -17`. SIGKILL is 9 on both, and on every Unix still in service; it is the one number safe to carry in your head.

`ps -o state=` is the other, and section 5 hides it on purpose. On Linux the `state` column is one letter, and the flags live in a separate `stat` column; on a Mac `state` is another name for `stat` — the letter, then flags about the process that have nothing to do with this lesson. Without its `cut -c1`, section 5 printed `T` for the stopped child on macOS 26 on x86-64 and `T<` on `macos-latest` on arm64, where `<` is BSD `ps` reporting a raised CPU scheduling priority. Nothing in the script changes a priority, so the child can only have inherited it from the runner; `N` is the opposite flag, for a process started under `nice`. Cut to its first character — the run state, where `T` means stopped on both — section 5 reads identically on both.

## In zsh and fish

Both catch the same signals bash does, neither can catch SIGKILL or SIGSTOP, and each has its own spelling.

**zsh** takes bash's `trap` unchanged, and adds a second form: a function named `TRAPINT`, `TRAPQUIT` or `TRAPTERM` *is* the handler, with no `trap` command anywhere. It reads better once a handler is more than one line, and it is zsh-only — bash sees a plain function that nothing calls. One other difference matters before you copy a script across: bash turns job control on inside a script with `set -m`, and zsh refuses in a non-interactive shell and says so.

**fish** has no `trap` builtin at all. A handler is a function:

```fish
function on_int --on-signal INT
    echo "caught SIGINT -- not stopping"
end
```

The `trap` you can still type in fish is a compatibility *function* that defines one of these for you. Two fish-specific findings came out of running the same script there. `--on-signal QUIT` is accepted and **never fires**, while `--on-signal TERM` declared beside it does — so Ctrl-\, the key that ends a program whose SIGINT handler has taken over, does nothing to a fish script either, and that is fish's decision rather than the kernel's. And fish has no `kill` builtin, so `kill -l KILL` is whatever `/bin/kill` your system ships: GNU answers `9`, BSD prints its usage and exits non-zero.

## If you are coming from another library

**In a program rather than a shell**, the same three rules apply and the ergonomics differ completely. [Ctrl-C is a signal ↗](https://masiarek.github.io/python-learning-library/02_Projects_and_Environments/ctrl_c_is_a_signal/index.html) in the Python library is the counterpart to section 1: `KeyboardInterrupt` is not what Ctrl-C does, it is what Python's default SIGINT handler does with it, and `signal.signal()` replaces that handler in one line. [Catching a signal ↗](https://masiarek.github.io/rust-learning-library/09_Advanced/catching_a_signal/index.html) in the Rust library is the other extreme: there is no signal API in `std` at all, so Ctrl-C ends the process with no unwinding and no destructors until you declare `signal` from libc yourself.

**The signal this page does not cover** is SIGPIPE, which is what turns up when the reader of your pipeline quits early. [`head` closes the pipe early](../../01_Pipelines/head_closes_the_pipe_early/README.md) has it, including the 141 that is 128 + 13.

**Which thread receives a signal** in a program that has several is a question of its own: [Signals ↗](https://masiarek.github.io/concurrency-learning-library/11_Concepts/communication/signals/index.html) in the concurrency library.
